server

前面我们讲到，ServiceCache 里注册了 11 个服务，而注册这个动作发生在 BinderProvider.init() 里。那问题就来了：这 11 个服务是干什么的？除了服务，server 还提供了别的东西吗？

lib/src/main/java/com/lody/virtual/server/ 这个目录，一共 22,502 行、13 个子包。我们把它拆成三块来看：服务、组件，以及它们怎么配合。

server提供组件

光有服务还不够。

服务是给"我们自己人"用的——客户端的 VActivityManager 通过 Binder 找到它。但系统不会调用服务，系统只认 virtualapp本身在manifest 里声明的组件。虚拟应用的组件在系统里根本不存在，所以凡是"系统要回调 VA"的场景，都必须有一个真实存在的组件顶上去。

于是就有了这些组件。lib 模块的 :x 进程里一共 16 个，按 Android 四大组件分类：

Activity（8 个）

组件 干什么
ShadowPendingActivity 接住虚拟应用的 PendingIntent.getActivity()
ShortcutHandleActivity 桌面快捷方式点进来的跳板
ChooserActivity 顶替 Intent.createChooser() 的分享面板
ResolverActivity 顶替隐式 Intent 的"用哪个应用打开"
ChooseAccountTypeActivity 账户类型选择
ChooseTypeAndAccountActivity 账户选择
WindowPreviewActivity 启动前显示窗口背景预览（防止白屏）
RequestPermissionsActivity 替虚拟应用弹运行时权限

Service（5 个）

组件 干什么
KeepAliveService 保活，START_STICKY
HiddenForeNotification 显示一个隐藏的前台通知，提高 :x 优先级
ShadowPendingService 接住 PendingIntent.getService()
ShadowJobService 虚拟应用 JobService 的系统侧入口
ShadowJobWorkService Job 真正执行的地方

Provider（2 个）

组件 干什么
BinderProvider 服务注册表入口，call("@") 返回 IServiceFetcher
ContentProviderProxy 虚拟应用 Provider 的请求转发

Receiver（1 个）

组件 干什么
ShadowPendingReceiver 接住 PendingIntent.getBroadcast()

这些组件按用途其实分三类：

  1. 虚拟应用的代理——就是 :p0..:p99 里那 399 个槽位组件（ShadowActivity$Pn 之类）。系统只认组件名，所以每个虚拟应用进程都得有一个合法名字顶着。
  2. 系统 API 的回调接收器——比如 PendingIntent、JobScheduler、选择器这些 API，系统要求目标组件必须真实存在，那就用 ShadowPending*、ShadowJob* 去接。
  3. VA 自己用的——BinderProvider（注册表入口）、KeepAliveService、ShortcutHandleActivity（快捷方式）这些。

把它们都放在 :x (server进程)里，是因为这些组件必须比虚拟应用活得久——虚拟应用进程死了，Job 还得能触发，PendingIntent 还得能响，:x 不能跟着挂。
